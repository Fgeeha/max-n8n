# Сценарии демо-бота

Витрина возможностей связки n8n + MAX. Разделение простое:

- **Контент** — тексты экранов, кнопки, товары — в таблицах `bot_screens` и
  `bot_products`. Правится формами «Админка контента» (`/form/maxbot-screens`,
  `/form/maxbot-products`, Basic Auth) или прямо в базе. Бот подхватывает на
  следующем сообщении.
- **Логика** — какой экран показать и что запомнить между шагами — одна нода
  **«Сценарий»** в `workflows/max-bot-core.json`.
- **Отправка** — отдельный сценарий `max-bot-send`, переиспользуемый элемент
  без кода: принимает `{ chat_id, user_id, callback_id, text, buttons }` и сам
  решает, `/messages` это или `/answers`.

## Карта экранов

```
/start ─► Главное меню
            ├─ 🏢 О компании ──► текст + [🌐 сайт] [📋 скопировать телефон] [⬅️ назад]
            ├─ 📋 Каталог ─────► список товаров
            │                      └─► карточка товара (описание, цена)
            │                            ├─ 🛒 Заказать ──► форма (2 шага)
            │                            └─ ⬅️ В каталог
            ├─ 💱 Курс валют ──► запрос к API ЦБ РФ, [🔄 обновить]
            ├─ 🧾 Мои заказы ──► выборка из Postgres
            ├─ 📍 Я рядом? ────► request_geo_location, бот отвечает координатами
            └─ 🌐 Документация MAX (внешняя ссылка)

текстом:  /whoami — свой user_id   ·   «эхо <текст>» — повтор
```

## Что чем демонстрируется

| Экран | Что показывает |
|---|---|
| О компании | три типа кнопок сразу: `link`, `clipboard`, `callback` |
| Каталог и карточки | генерация кнопок из данных: добавили товар — кнопка появилась сама |
| Форма заказа | многошаговый диалог с состоянием в `dialog_state` |
| Курс валют | обращение к внешнему API и подмешивание данных в ответ |
| Мои заказы | чтение из Postgres в ответ на нажатие |
| Я рядом? | приём геопозиции от пользователя |
| /whoami | свой `user_id` — нужен, чтобы вписать себя в `ADMIN_IDS` |

## Форма заказа подробно

```
[🛒 Заказать]                 → dialog_state: {screen:'order', step:'qty', data:{product_id}}
   ↓ id товара уже запомнен, спрашивать не надо
Шаг 1: сколько штук?          → кнопки 1 / 2 / 5  ИЛИ число сообщением
   ↓                             dialog_state: step:'phone', data:{product_id, qty}
Шаг 2: как связаться?         → [📱 отправить контакт]  ИЛИ телефон сообщением
   ↓                             телефон достаётся из vCard вложения contact
INSERT INTO orders … RETURNING id
   ↓
✅ клиенту: «Заказ №N принят»   +   🔔 каждому из ADMIN_IDS: детали заказа
   ↓
dialog_state очищается — следующее сообщение снова читается как команда
```

Пока форма открыта, ввод перехватывается ею: «3» на шаге количества — это
количество, а не команда. Кнопки навигации (`⬅️ назад`, `✖️ отменить`) работают
всегда, иначе из формы было бы не выйти.

Незаконченная форма живёт `FORM_TTL_MINUTES` (30 минут) и убирается
`prune_bot_events()` — иначе пользователь, ушедший на шаге «жду телефон»,
остался бы в нём навсегда.

### Куда уходит заказ

В `orders` и сообщением каждому `user_id` из `ADMIN_IDS`. Свой id можно узнать
командой `/whoami` и вписать в `.env`:

```env
ADMIN_IDS=297701163,111222333
```

Пустой `ADMIN_IDS` — уведомлять некого, заказ всё равно ложится в базу.

**Важно:** правки `.env` доезжают до контейнера только при пересоздании.
`make provision` делает `up -d --force-recreate`; `docker compose restart`
переиспользует старое окружение, и новый `ADMIN_IDS` не подхватится.

## Как добавить своё

**Новый экран** — форма `/form/maxbot-screens`: ключ `delivery`, текст,
кнопки JSON. Затем кнопка с `payload: "delivery"` на любом экране (например,
переписать экран `main` той же формой). Кода нет: «Сценарий» показывает любой
ключ из `bot_screens` по совпадению с `payload`.

**Новый товар** — форма `/form/maxbot-products`. Кнопка в каталоге, карточка
и форма заказа собираются из шаблонов `catalog_button`, `item`, `order_*`.
Снять с продажи — «В каталоге: нет», история заказов при этом сохраняется.

**Плейсхолдеры** в тексте и кнопках: `{name}` `{user_id}` `{chat_id}` — из
события; `{id}` `{title}` `{short}` `{description}` `{price}` — товар;
`{qty}` `{total}` `{phone}` `{order_id}` `{client}` — заказ; `{lat}` `{lon}`
`{echo}` `{rates_date}` `{rates_lines}` `{orders}` — экранно-специфичные.
Неизвестный плейсхолдер остаётся в тексте как есть — так его видно.

**Обязательные ключи**, которых «Сценарий» ждёт в таблице: `main`, `catalog`,
`catalog_button`, `item`, `order_qty`, `order_qty_bad`, `order_phone`,
`order_phone_bad`, `order_done`, `order_admin`, `cancel`, `rates`, `myorders`,
`myorders_empty`, `whoami`, `geo`, `echo`. Их проверяет `make test` по
`db/seed/bot_content.json`; если ключ удалить из базы, бот покажет
«⚠️ Экран не найден» вместо падения.

**Новый шаг формы** — единственное, что требует кода: ещё одна ветка по
`state.step` в «Сценарии» и шаблон экрана в `bot_screens`.

**Отправить сообщение из другого сценария** (рассылка, напоминание) — нода
Execute Workflow на `max-bot-send` с item `{ chat_id, text, buttons }`.
Ошибки MAX API попадут в `bot_send_failures` автоматически.

## Что ещё стоит показать

Идеи по возрастанию трудоёмкости. Ни одна не реализована — это список, а не
описание существующего.

| Идея | Что демонстрирует | Трудоёмкость |
|---|---|---|
| FAQ по кнопкам | вложенные меню без состояния | только строки в `bot_screens` через форму |
| Квиз с подсчётом баллов | накопление в `dialog_state.data` | одна ветка в «Сценарии» |
| Отзыв с оценкой ⭐1–5 | callback + запись в новую таблицу | таблица + нода Postgres |
| Погода по геопозиции | внешний API + данные пользователя | как «Курс валют» |
| Рассылка по `bot_users` | массовая отправка из базы | Postgres + Execute Workflow на `max-bot-send` |
| Статусы заказа | админ меняет статус кнопкой, клиенту уходит уведомление | ветка админ-меню |
| Прикрепление фото к товару | `POST /uploads` и вложение `image` | загрузка файла двумя запросами |
| Оплата ссылкой | кнопка `link` на платёжную форму, вебхук о платеже | второй вебхук в n8n |
| Передача оператору | пересылка диалога в чат поддержки | работа с групповым чатом |
| Напоминание «вы не закончили заказ» | Schedule + выборка протухших `dialog_state` | отдельный сценарий по расписанию |

Последняя особенно наглядно показывает, зачем здесь n8n: это отдельный
сценарий по расписанию, который ходит в ту же базу и шлёт сообщения — писать
его в коде бота пришлось бы отдельным воркером.

## Ограничения демо

- Каталог — таблица `bot_products` без остатков, фото и категорий. Для
  настоящего магазина товары приедут из внешней системы: заменить SELECT в
  ноде «Состояние и контент» на HTTP Request к ней.
- Админка — две формы n8n без списка существующих записей: чтобы посмотреть,
  что есть, нужен `make db-shell` или редактор n8n.
- Корзины нет: один заказ — один товар. Мультитоварная корзина требует
  накопления позиций в `dialog_state.data.items`.
- Оплаты и статусов доставки нет, `orders.status` меняется только руками.
- Телефон из текста проверяется грубо (10–15 цифр), без нормализации формата.
