# Итог проверки: n8n как no-code платформа для бота MAX

Дата проверки: 2026-09-04. n8n 2.37.10, Bot API MAX (`botapi.max.ru`).

## Что проверено вживую

Полный round-trip подтверждён историей выполнений n8n (`make executions`):

| Выполнение | Событие | Действие сценария |
|---|---|---|
| 33 | `/start` в личке | `POST /messages` — главное меню с кнопками |
| 34 | нажата «📞 Контакты» | `POST /answers` — экран заменён на месте |
| 36 | нажата «📋 Каталог» | `POST /answers` — подменю каталога |
| 35 | нажата «⬅️ Назад» | возврат в главное меню |

Плюс:

- Опрос идёт стабильно, каждые 10 секунд, без ошибок.
- Стартовый прогон разобрал 38 накопившихся сообщений из групповых чатов
  и **не отправил ни одного ответа** — фильтр по `chat_type` сработал на
  боевых данных.
- Форма тела сообщения (`inline_keyboard`, `callback`, `link`,
  `request_contact`, `format: markdown`) принята живым API.
- `make test` — 7 проверок логики на фикстурах.

## Ответ

**Да, но «no-code» получается не полностью — примерно на 70%.**
Для меню, кнопок и ветвления n8n подходит. Для разбора апдейтов и хранения
состояния всё равно нужны две JS-ноды.

## Что получилось без кода

- **Кнопки и меню.** Inline-клавиатура MAX — обычный JSON во вложении. Меню
  описано декларативно одним объектом; чтобы поменять надписи, порядок,
  ряды или добавить экран, достаточно отредактировать этот объект в UI n8n
  и нажать Save. Перезапуск не нужен.
- **Ветвление сценариев.** Нода Switch разводит поток по условиям
  штатными средствами UI. В сценарии показаны две ветки: «эхо» и «меню»,
  обе сходятся в одну ноду отправки.
- **Вызовы Bot API.** Ноды HTTP Request. Отправка сообщений и ответы на
  нажатия кнопок — один и тот же узел, метод подставляется выражением.
- **Секреты.** Токен читается выражением `{{ $env.MAX_BOT_TOKEN }}`, в базу
  n8n и в экспорт сценария не попадает.
- **Наблюдаемость.** История выполнений n8n показывает каждый апдейт с
  входом и выходом каждой ноды — отладка сценария заметно приятнее, чем
  чтение логов бота.

## Где код всё-таки понадобился

Две ноды Code, обе неустранимы штатными средствами:

1. **Разбор `GET /updates` и хранение marker.** У n8n нет ноды MAX, а marker
   надо где-то держать между запусками. Единственный встроенный механизм —
   `$getWorkflowStaticData()`, доступный только из Code. Плюс здесь же
   нормализация `message_created` и `message_callback` к одной структуре,
   иначе всё дальше пришлось бы дублировать на два потока.
2. **Сборка ответа по меню.** Формально разложимо на Set + Switch по одному
   узлу на экран, но тогда добавление экрана = правка графа, а не данных.
   Один объект `MENU` в Code оказался ближе к «no-code» по смыслу: правится
   как конфиг, а не как схема.

Вывод: **чем сложнее сценарий, тем меньше доля кода.** Стоимость этих двух нод
фиксированная, а меню, ветки и экраны дальше растут без единой строки.

## Чего в этой сборке нет

| Ограничение | Как снимается |
|---|---|
| Long polling вместо вебхука, задержка ≤10 с | См. ниже |
| SQLite | Postgres в compose |
| Одна реплика (marker в static data одного инстанса) | Вебхук + внешнее хранилище состояния |
| Нет диалогов с памятью (многошаговые формы) | Хранить состояние на `user_id` во внешней БД, static data для этого не годится |
| n8n без авторизации на `0.0.0.0:5678` | Reverse-proxy с basic auth или доступ только с localhost |

### Переход на вебхук

Long polling выбран потому, что работает без публичного адреса — этого
достаточно, чтобы проверить гипотезу локально. В проде правильнее вебхук:

1. Поднять n8n за HTTPS-доменом, выставить `N8N_WEBHOOK_URL`.
2. В сценарии заменить Schedule Trigger + «Прочитать marker» + `GET /updates`
   на ноду **Webhook** — она отдаёт тело апдейта сразу, marker не нужен,
   и первая Code-нода схлопывается до нормализации.
3. Зарегистрировать адрес:

```bash
curl -X POST -H "Authorization: $MAX_BOT_TOKEN" -H 'Content-Type: application/json' \
  -d '{"url":"https://<домен>/webhook/max","update_types":["message_created","message_callback","bot_started"]}' \
  https://botapi.max.ru/subscriptions
```

Важно: вебхук и long polling **нельзя держать одновременно** — они делят одну
очередь обновлений и будут отбирать апдейты друг у друга.

## Практические грабли, на которые стоит закладываться

- **Один токен — один потребитель.** Второй запущенный бот на том же токене
  съест обновления. На этой машине уже крутится другой MAX-бот (`docker-bot-1`);
  токены разные, конфликта нет, но проверять это стоит явно.
- **Очередь копится молча.** Если сценарий выключен, апдейты накапливаются и
  при включении прилетают пачкой. `make bot-reset` подтверждает хвост.
- **Групповые чаты.** Боевой токен состоял примерно в 20 реальных домовых
  чатах (от 40 до 270 участников). Без фильтра по `chat_type === 'dialog'`
  первый же тестовый запуск ушёл бы к жителям. Фильтр стоит по умолчанию.
- **Compose и имя проекта.** Без `name:` в compose-файле Compose берёт имя
  каталога (`docker`) и склеивает стек с чужим. `down -v` в такой конфигурации
  снёс бы чужой том с данными.
- **Схему сообщения можно проверить, ничего не отправляя** — API валидирует
  тело до поиска чата, см. `docs/max-bot-api.md`.
- **База n8n в режиме WAL.** Если смотреть выполнения через копию
  `database.sqlite` без `database.sqlite-wal`, видно устаревший снимок на
  момент последнего чекпоинта, и кажется, что сценарий встал. `make executions`
  копирует WAL вместе с базой.

## Когда n8n здесь не подойдёт

- Высокая нагрузка и низкая задержка: каждый апдейт — это отдельный запуск
  сценария с накладными расходами.
- Сложные многошаговые диалоги с состоянием: получится, но через внешнюю БД,
  и выигрыш в «no-code» съедается.
- Логика, которую всё равно писать кодом: тогда обычный бот на
  библиотеке проще и дешевле в поддержке.

Сценарии, где n8n выигрывает: меню, справочные боты, заявки, маршрутизация
обращений, интеграции с CRM/таблицами/почтой — то есть всё, где ценность в
связке с другими системами, а не в самой логике бота.
